# Handover — 27 September 2026

For teammates with robot access. No jargon that isn't defined right where it's used.

## What changed, in five lines

1. The corpus grew from **1,104 to 1,290 documents** (columns, books, speeches, and biography chapters).
2. The topic map that routes a question to a subject was rebuilt from **34 deployed dimensions to 30**,
   derived from the whole corpus instead of a 79-document sample.
3. A second, faster answer engine — no live routing call, local search instead — is now **reachable**
   behind a setting called `CJ_PIPELINE`, but is not switched on (see below).
4. **`knowledge-base/`** is a reading copy of the corpus for the Foundation: the source text, spreadsheets,
   and a plain-language README, with no application code.
5. **`Bundle Folder/`** is the data-plus-code package for the robot itself.

## The robot's behaviour does not change when you install this

`CJ_PIPELINE` defaults to `legacy` — the same Haiku-router engine the robot has run for months. Copying
any of this to a robot, or installing a fresh one from this release, does **not** change what it says or
how it decides what to say. The new engine exists and can be tested, but nothing switches to it
automatically.

## How to get it

- **A fresh robot:** `git clone -b release/kb-v2-2026-09-27 https://github.com/Supervaise-Inc/CJAP.git`.
  This is an immutable tag — cloning it today or in six months gets the exact same content. Do not clone
  `pi/deployment-snapshots`; that branch now records what a live robot's filesystem currently looks like
  (via `snapshot-push.sh`), not what a fresh install should get.
- **Pulling into an existing checkout on this machine or another:** `git pull` on `deliverable/2026-09` —
  it now has an upstream on GitHub, so this works like any other branch from here on.

## What to copy to the Pi

**`Bundle Folder/cjap-bundle/` is the payload — copy that, not `Bundle Folder/` itself.** The outer
folder's name has a space in it, which is harmless on a USB stick or a Windows desktop and breaks
`rsync`, `scp`, and the robot's own service paths the moment it lands on Linux. `cjap-bundle/` has no
space in its name for exactly that reason.

`Bundle Folder/READ_ME_FIRST.md` has the numbered steps; the short version:

1. **Check free space on the Pi first**: `df -h /home/pollen`. You need **at least 1.5 GB** free — the
   payload is 516 MB, and the rest is headroom for the transfer and the copy it replaces.
2. Copy it: `rsync -a --info=progress2 "cjap-bundle/" pollen@<hostname>.local:~/data_bundle_incoming/`
3. Verify on the robot: `sha256sum -c checksums.sha256` — every line must say `OK`.
4. Move it into place and restart the service (`READ_ME_FIRST.md` has the exact commands).

## If something goes wrong

- A transfer that fails partway never overwrites the robot's working copy — it lands in a temporary
  folder first (step 2 above), so the robot keeps running on what it had until you explicitly move the
  new copy into place.
- The pre-release state of the old `pi/deployment-snapshots` branch is preserved at the git tag
  **`pi-snapshot-pre-kbv2-2026-09-27`** (pushed, on GitHub) if you ever need to see exactly what a robot
  looked like before this release existed.

## What not to do

- **Do not set `CJ_PIPELINE=retrieval`** on any robot before you're told the CE-11 → CE-14 sign-off has
  passed (see the open gate below). It's reachable for testing, not for live use.
- **Do not force-update `pi/deployment-snapshots`** to match this release. That branch's job is
  recording what a live robot's filesystem actually looks like, via `snapshot-push.sh` — it is not a
  target for engineering work to push *to*. Forcing it would also break `git pull` for any robot already
  tracking it (the two branches share no common git history at all, so it isn't a normal update).
- **Do not move the release tag.** `release/kb-v2-2026-09-27` is meant to never change. The next release
  is a new tag with a new date, not this one edited in place.

## The one open gate

**CE-11 → CE-14 must pass before `CJ_PIPELINE=retrieval` becomes the default.** That work validates the
new engine against a gold question set on the current 1,290-document corpus (the old comparison,
`arch_baseline_v2`, only covered 827 documents and predates the current search model, so it can't be
reused as-is — a fresh baseline is part of that gate). Three numbers it has to beat or explain:

- **Routing accuracy**: 86.7% of questions are routed to the right subject on the first try in testing so
  far, but `twin_beacons_doctrine` — the project's own signature idea — never won a version of its own
  question in that test.
- **A 2.9-point drop** in one retrieval quality measure (hit@10) on a frozen 40-question set, after the
  subject map was rebuilt — everything else on that set held steady.
- **18 documents** that no subject claims at all under the current map.

This is tracked as **batch-05**, a new body of work, not a continuation of this one. Until it clears,
treat the new engine as available for testing and demonstration prep, not for the robot people actually
talk to.
