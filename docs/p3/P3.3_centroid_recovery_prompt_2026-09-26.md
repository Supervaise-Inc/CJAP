# P3.3 — centroid collapse: what happened, and the recovery prompt

**26 Sep 2026. This was my error, not Claude Code's.** Prompt B told it to run
`scripts/merge_tag_topics.py` and called that "RETAG ONLY". The script's own first line says
*"W1.7 Steps 4-5 — **merge centroids**, full-corpus orphan scan, tag the pilot subset."* Merging is step
4a and it is not optional. CC ran exactly what it was told to run, spotted that the result was wrong,
stopped before doing anything else, and preserved a rollback candidate without restoring it. That is the
right behaviour in every respect.

## What actually happened, verified

`merge_tag_topics.py` merges every centroid pair whose cosine exceeds `TOPIC_MERGE_COSINE` (0.95) by
union-find, averages each group, and overwrites `data/index/topic_centroids.npy` + meta.

Measured on the archived pre-run 34-topic set:

| Pairs above | Count (of 561) |
|---|---:|
| 0.99 | 11 |
| 0.98 | 41 |
| 0.95 | **220** |
| 0.90 | 477 |

`max off-diagonal cosine 1.0000 · mean 0.9334 · min 0.7533`

With 220 of 561 pairs over the threshold, union-find chains them into one giant component. **34 → 3 was
the only possible outcome.** This was not a re-run artefact and it was not bad luck; running that script
against this centroid set always collapses it.

### The near-collinearity is known and recorded — do not treat it as new damage

The archived meta records it from the July build itself:

```
separation_mean_pairwise_cos : {"old_pilot_scoped": 0.9171, "new_full_corpus": 0.9334}
```

0.9334 is what the builder measured and accepted. Averaging many chunk vectors of one author writing in
one domain pulls every centroid toward the corpus mean; that is ordinary for bge-base, and the router
uses a **softmax over the cosines**, not the raw values, so small differences still separate. The prior
biases, it never gates. Nothing here needs redesigning mid-correction.

### But the identical pair is a real defect worth logging

`honors_received` and `robot_identity_meta` are **byte-identical vectors** (max abs diff 0.0). The meta
explains why:

```
gmean_fallback_topics  : ["honors_received", "robot_identity_meta"]
thin_topics_lt3_chunks : [["honors_received", 0], ["robot_identity_meta", 0]]
```

Both topics have **zero chunks**. The builder gave each the same geometric-mean fallback vector, so the
router can never tell them apart. This shows up in the existing gold set: X31 *"Who are you?"* routes to
`robot_identity_meta`, and X35 *"What's the weather in Manila today?"* — an out-of-scope probe — routes
to `honors_received`. Same vector, so an OOS question lands on an empty honours topic. Log it for CE-8;
do not fix it during a correction batch.

### No fresh backup was taken — CC is right about the cause

The script snapshots to `topic_centroids_premerge.npy` only if that file does not already exist. It
does: **(35, 1024), 22 Sep — the bge-large 35-topic set from the June bakeoff.** Wrong model, wrong
dimensionality, and it silently disables the guard. `data/index/` is not tracked by git at all
(`git ls-files data/index/` returns nothing), so there was no VCS rollback either.

**The rollback CC preserved is the right one.** `_archived_precollapse_2026-07-17_topic_centroids.npy`
is (34, 768), bge-base, `build_date 2026-07-17`, `corpus_dense_build_date 2026-07-17` — matching the
pre-run meta exactly. The Final Project Folder was synced from the working repo on 22 Sep and the
centroids were never rebuilt after, so the two are the same file.

### Why restoring stale July centroids is correct, not a compromise

Holding the topic map fixed while the corpus changes is the whole point of CE-7. Centroids are vectors
in the bge-base space; they do not reference chunk ids at query time, so batch-03 changing 156 documents
does not invalidate them. Rebuilding them would be `build_centroids.py`, which stays banned until after
CE-12 — changing the topic map and the corpus in one run makes the promotion eval unreadable.

## Three open items, logged not fixed

**1. `merge_tag_topics.py` is not idempotent and has no guard.** It re-merges whatever it is given,
and its backup only fires when `topic_centroids_premerge.npy` is missing. Two cheap fixes for after
CE-12: make the backup unconditional (timestamped), and refuse to run when the input meta already
carries `merged_from`. Neither may be done now — the script is in the attributable path for this batch.

**2. `check_date_index.py` imports a module `service` that does not exist in this repo.** Pre-existing,
unrelated to batch-03. P3.5's substance was verified anyway: `build_date_index.py` exited 0 at
1104/1104/0 with a sha256 identical to the before-value, which is what VERIFY 6 actually asked for.
Logged as a defect for batch-05.

**3. `scripts/make_runtime_dense_index.py` exit-code wording.** Two weaknesses: the "already exists, use
--force" guard returns 3, which reads as a failure in a chain when it is a deliberate refusal; and if
`chunks.jsonl` ever holds *fewer* chunks than the matrix, `extra` goes negative and the message prints a
negative count. Both are cosmetic — the script never wrote anything wrong — and both get fixed after
CE-12. CC should say which line it meant by "line 185"; on the committed copy that line is the max-norm
print, so the numbering may differ.
