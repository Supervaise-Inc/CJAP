# Parity matrix — `answer_pipeline.py` (legacy) vs. `service.py` (retrieval)

`answer_pipeline.py` has been the live path for months and has accumulated behaviour
`service.py` — a much smaller, single-purpose module (routing + retrieval + composition, nothing
else) — never had reason to grow. This is the inventory Phase 8 asked for: every behaviour, whether
`service.py` has it, and what it would take to add. **Ranked by what a visitor would notice first; a
missing filler is cosmetic, a missing refusal path is not.**

Only one row was closed in this phase (identity — see the note under it). Everything else below is
reported, not built, per the phase's own instruction.

| # | Behaviour | `answer_pipeline.py` | `service.py` | Visitor impact | Cost to add |
|---|---|---|---|---|---|
| 1 | **Out-of-scope refusal** | 3-way Haiku classifier (`input_gate`) routes `out_of_corpus` straight to a canned deflection, router and composer both skipped | none — `OUT_OF_SCOPE_THRESHOLD` only re-weights the topic prior toward uniform; the composer is asked, in its system prompt, to decline in prose (`COMPOSER_OOS_DECLINE_TEXT`), but nothing hard-stops it from trying anyway | **High.** "What's your favorite recipe?" answered with only a soft prompt nudge is the single most visible way this pipeline could embarrass itself on stage | **Medium.** `retrieval.route()`'s `in_scope` boolean already exists; wire a hard branch in `service.answer()` that returns a canned decline when `not in_scope`, the same shape `answer_canned.get("out_of_topic")` returns today |
| 2 | **Identity intent** (persona answer, 120-token budget) | `force_meta_routing()` + `TOKEN_BUDGET_BY_DIM["robot_identity_meta"]` | **Closed in Phase 8.** `retrieval.input_gate()`'s existing detection now reaches `service._answer_identity()`, which answers from `topic_map.json`'s `robot_identity_meta` definition text at the same 120-token cap. Verified: 0/20 non-identity queries changed, both identity test queries now route to the intent (`batch-04/ph8_analysis/results/identity_fix_check.json`) | High (was) | Done |
| 3 | **Answer gate** (pre-TTS keyword recheck + post-hoc fact-check for invented years) | `answer_gate.py`, dark by default (`ANSWER_GATE_ENABLED=False`), wired through `speech_streaming.stream_turn()` | none | **High when enabled.** This is the deterministic, $0 backstop against a self-description slip ("I am an AI") or a fabricated year reaching speech — exactly the failure mode a demo cannot afford | **Medium.** `answer_gate.check_answer()`/`fact_check()` take a sentence + context + topic ids — plumbable onto `service.compose_streamed`'s per-sentence stream the same way `stream_turn()` already does it |
| 4 | **Fidelity check** (post-hoc Haiku sampler for hallucination / voice drift / guardrail violation) | `fidelity_check()` + `generate_response_with_fidelity()`, one retry on flag | none | **Medium-high.** Catches what the answer gate's fixed rules can't (a plausible-sounding but ungrounded claim) | **Medium**, but reintroduces a second LLM call — after composition, not before, so it does not touch `llm_calls_before_composition`, but it does add latency and cost per turn, worth an explicit decision rather than a silent port |

| 7 | **Language gate** (reject ASR hallucinations in languages other than English/Filipino/Taglish) | `text_language_gate.py` is what `main_voice_robot.py` actually imports; **`lang_gate.py` is a separate, differently-implemented module used only by `app/cj_voice_cloud.py`**, an entry point nothing deploys — so this is not one behaviour with one gap, it is two implementations already, one live, one not | none | **Medium**, only under room noise (the failure mode `text_language_gate.py` exists for: a Whisper hallucination in Dutch or Latin) | **Medium.** Same shape as row 5 — a pure function over the raw transcript, callable before it reaches `retrieval.run()` |

Sentence-level streaming for the retrieval path is future work | **Large.** Reimplementing `SentenceSpeaker`-equivalent sentence buffering, gesture styling and caption publishing against `service.py`'s `on_text` stream is a project in itself |
| 9 | **Speaker verification / voice lock** | `voice_identity.py`, live; `speaker_id.py` is a *different* implementation (WeSpeaker CAM++ ONNX) used only by `cj_voice_cloud.py` — same two-implementations pattern as row 7 | none | **Low-medium**, and only visitor-visible when voice lock is enabled at all (it gates who the robot will answer, not what it says) | Not a `service.py` concern — voice lock runs before the question ever reaches a pipeline |
| 10 | **Per-topic token budget** (`TOKEN_BUDGET_BY_DIM`: longer answers for some dimensions, shorter for others, dynamically scaled) | yes | no — flat `COMPOSER_MAX_TOKENS` (480) / `COMPOSER_TARGET_PARAGRAPHS` ("3-5") for every topic | **Low.** Shows up as answer length feeling generic rather than tuned per subject, not as a wrong answer | **Small.** `service.py` already threads a topic id (`ri["top_topic"]`) through `_directives()`; a lookup table the same shape as `TOKEN_BUDGET_BY_DIM` slots in at `compose_streamed`'s `max_tokens` |
| 11 | **Usage meter** ($ tally for the maintenance dashboard, `~/cj_usage.json`) | `usage_meter.py`, wired into both `answer_pipeline.py` and `cj_chat.py` | none | **Low**, operator-facing only, not visitor-facing | **Small.** One hook after each `service.compose_streamed()` call, same call shape `answer_pipeline.py` already uses |

## Two findings that are not gaps in `service.py`, but are worth fixing anyway

- `postprocess.py` and `text_entities.py` are byte-identical. `postprocess.py` is imported nowhere.
- `dynamic_filler.py` and `answer_filler.py` are byte-identical. `dynamic_filler.py` is imported nowhere.
- `lang_gate.py`, `speaker_id.py`, `answer_gate.py` and `dynamic_filler.py` are all imported by
  `app/cj_voice_cloud.py`, an entry point nothing deploys (`answer_gate.py` is *also* reachable from the
  live `speech_streaming.py`, so it is not orphaned — just dark by default there). None of this changes
  what ships in `deploy/pi/bundle/`; it is a housekeeping note for whoever next has to read this codebase
  cold.

## What Phase 8 built, and what it left for later

Built: row 2 (identity). Everything else above is reported at the size and rank the phase asked for,
not built — rows 3–6 look like the next-most-valuable additions if `CE-11 → CE-14` clears and
`CJ_PIPELINE=retrieval` is heading toward becoming the default; row 8 is the long pole before that
default flip could mean anything on stage, since a demo needs the retrieval path to *speak*, not just
compose.
