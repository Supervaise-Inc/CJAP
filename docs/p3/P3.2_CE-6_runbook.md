rows and compares them to `pilot_dense.npy`. Two checks, in this order:

```python

...
```

**Both would have failed**, because `pilot_dense.npy` was built on **17 July** against the

**And the gate runs *after* the embed** — line 145, once the full matrix exists. On CPU that is a ~10-hour

## 2. Backend — choose before you start

`config.py` defaults to **`cuda_fp32`** with `EMBED_BATCH_SIZE=8`, and the comments record a GTX 1650 with
~3 GB free VRAM, so the GPU path is the one this machine has been built for.

| Backend | Speed | 9,804 chunks |
|---|---|---|
| `cuda_fp32` (default) | fast | minutes to low hours |
| `cpu_fp32` | ~0.27 chunks/s (benchmarked on this machine) | **~10 hours** |

If the GPU is unavailable, set `CJ_EMBED_BACKEND=cpu_fp32` and `CJ_EMBED_DEVICE=cpu` and start it
overnight. **Do not mix**: the backend is recorded in the index meta precisely so two regimes can never
be combined.

There is a resume checkpoint, keyed on `(EMBED_MODEL_ID, EMBED_BACKEND, EMBED_NORMALIZE, chunk_index
sha256, chunk-set hash)`. An interrupted run resumes; a run with any of those changed discards the
checkpoint rather than resuming into a mixed set. So an interrupted overnight CPU run is recoverable, but
switching CPU→GPU mid-way starts over.

## 7. The pilot-index ruling (added 26 Sep)

`pilot_dense.npy` is both the July parity comparator *and*, on this machine, the index the app loads at
runtime. Archiving it cleared the parity gate and took the runtime index offline at the same time. Three
ways out — this needs a decision, not a guess:

1. **Point the runtime at the full corpus** — set `CJ_DENSE_INDEX_PATH` to `corpus_dense.npy` after the
   rebuild. Arguably what the system should have been doing since the full-corpus re-embed: the app then
   serves from all 1,104 documents rather than the 95-document pilot subset. Check with whoever set
   `DENSE_INDEX_PATH`'s default whether the subset was deliberate.
2. **Regenerate the pilot slice after the build** — a short script that takes the 95 allowlist doc_ids,
   pulls their chunk rows out of the new `corpus_dense.npy`, and writes `pilot_dense.npy` plus a fresh
   meta with the *current* chunk_ids. Ten lines, and it keeps the existing topology.
3. **Restore the archived July pair** — do not. Its chunk_ids are from the pre-correction chunk set and
   would fail the parity gate's missing-id check, which is what started this.

**Recommended: (1), with (2) as a fallback if anything depends on the subset index.** Either way, decide
before the rebuild, so the run and the runtime end up consistent.

### RULED — 26 Sep 2026

**Option 1 as written above is wrong and must not be used.** `app/retrieval.py:54` reads
`meta["doc_ids"]`, and the corpus meta that `build_corpus_dense.py` writes has no `doc_ids` key
(model_id, dim, backend, normalize, batch_size, version_block, n_chunks, build_date,
chunk_index_sha256, pilot_parity_sanity, chunk_ids — that is all of it). Pointing
`CJ_DENSE_INDEX_PATH` at `corpus_dense.npy` therefore raises `KeyError: 'doc_ids'` on the first query.

**The ruling is option 1's intent by way of option 2's mechanism, at full-corpus scope:**
`scripts/make_runtime_dense_index.py` (added 26 Sep) copies the full matrix to `pilot_dense.npy` and
writes a meta in the schema retrieval expects — `chunk_ids` **and** `doc_ids`, plus `n_docs`,
`allowlist_version`, `unresolved_docs`, `backend`, `derived_from`. No re-embedding, so the runtime
index and the corpus matrix stay bit-identical: one encoder, one dimensionality, one regime.

It verifies before it writes (shape vs chunk_ids, dim vs `EMBED_DIM`, model_id vs config, unit norms,
every chunk_id resolvable in `chunks.jsonl`, no extra chunks, no retired doc_id present), backs up any
existing pair, and on failure writes nothing. Its guards were tested against the current stale matrix on
26 Sep: it refused with "111 chunk_ids absent from chunks.jsonl" and wrote nothing.

**Consequence to record in the decisions register:** the runtime retrieval universe moves from the
frozen 95-document pilot subset (827 chunks) to all 1,104 documents (9,804 chunks). That is what the
answer pipeline is supposed to cover, but it is a change of behaviour, not a repair, and it should be
named as one.
