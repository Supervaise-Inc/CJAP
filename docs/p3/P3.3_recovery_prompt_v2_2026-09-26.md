different direction: `eval/results/arch_baseline_v4_2_provenance.json` — the 18 July full-corpus
promotion gate record — carries machine-verified `sha16` fingerprints of the **promoted** artifacts.
Hashing this repo's archives against them:

not a candidate; it is the promoted file, bit for bit. The whole v4.2 anchor set is intact in this repo,

not the `pilotmm` one.

## What the first run did, and what it did not

`merge_tag_topics.py` ran once with the default `TOPIC_MERGE_COSINE = 0.95` and wrote three things:
`data/index/topic_centroids.npy` + meta (34 → 3 topics, `merged_pairs: 220`), and
`reports/w1_7_orphan_review.json` + `w1_7_pilot_topic_tags.json`. **Nothing else was touched.** The
corpus, the pinned sheets, `corpus_dense.npy`, `pilot_dense.npy`, `pilot_sparse.pkl` and
`date_index.json` are all intact and correct. This is a three-file repair, not a rebuild.

It took no backup because its guard only fires when `topic_centroids_premerge.npy` is absent — and that
file exists as a **(35, 1024) bge-large** set from June, wrong model, wrong dimensionality, silently
disabling the guard. `data/index/` is untracked by git, so there was no VCS fallback either.

## Why it collapsed, so nobody re-runs it at 0.95

Measured on the restored set: **220 of 561 pairs exceed 0.95**; max off-diagonal 1.0000, mean 0.9334,
min 0.7533. Union-find chains them into one component, so 34 → 3 was certain. This is not a re-run
artefact — that script at that threshold always collapses this centroid set. The near-collinearity is
recorded in the July build itself (`separation_mean_pairwise_cos.new_full_corpus: 0.9334`) and the
router applies a softmax over the cosines, so the prior still discriminates. Nothing to redesign here.

**`honors_received` and `robot_identity_meta` are byte-identical vectors** — both have zero chunks
(`thin_topics_lt3_chunks`) and the builder gave both the same gmean fallback. Gold rows X31 and X35
route to those two topics. Log it for CE-8; do not touch it during a correction batch.
